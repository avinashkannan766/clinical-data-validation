# Clinical Trial Data Quality and Query Management Pipeline

## 1. Project Overview

**Project ID:** CTDM-001  
**Project Type:** Clinical Data Management Simulation  
**Tools:** Microsoft Excel, Python, pandas  
**Dataset:** Synthetic educational data  
**Status:** Study design and requirements definition

## 2. Purpose

The purpose of this project is to simulate a clinical data management workflow for a fictional clinical study.

The project will demonstrate how clinical study data can be structured, checked for quality, reviewed for inconsistencies, and managed through a documented query-resolution process.

This is an educational simulation and is not a real clinical trial.

## 3. Fictional Study Description

The fictional study investigates an investigational intervention in adults with elevated blood glucose.

- Planned participants: 30
- Study duration: 8 weeks
- Planned visits: Screening/Baseline, Week 4, and Week 8
- Data domains: Demographics, visit information, laboratory results, and adverse events
- Data management approach: Excel-based data organization with Python-assisted validation

The study design is illustrative and does not establish a real treatment protocol or medical recommendation.

## 4. Project Objectives

1. Design structured clinical data collection forms.
2. Create a data dictionary defining fields, data types, and validation requirements.
3. Generate synthetic participant and visit records.
4. Introduce controlled data-quality defects for testing.
5. Implement automated validation rules using Python and pandas.
6. Generate a discrepancy report and query log.
7. Document issue investigation, resolution, and change history.
8. Produce a reproducible data-quality summary.

## 6. Data Quality and Validation Principles

The validation pipeline will check for:

- Missing required fields
- Duplicate identifiers or records
- Invalid data types and date formats
- Dates that conflict with the study timeline
- Inconsistent subject identifiers across datasets
- Missing or incompatible units
- Values that violate explicitly defined study rules
- Inconsistencies between related records

An unusual value will not automatically be treated as an error. It will be flagged for review according to the applicable rule.

## 7. Query Management

Each identified discrepancy will have a unique issue or query identifier.

The query log will record:

- Query ID
- Subject ID and relevant record
- Field or domain involved
- Issue description
- Date identified
- Query status
- Response or investigation outcome
- Resolution details
- Closure status

The workflow will preserve the original input data. Corrections will only be recorded when supported by the simulation's documented source information and resolution rules.

## 11. Refined Study Design

- Planned participants: 30 synthetic participants.
- Study visits: Baseline, Week 4, and Week 8.
- Follow-up windows: Baseline is the reference visit; Week 4 is targeted for Day 28 ± 7 days; Week 8 is targeted for Day 56 ± 7 days after baseline.
- Treatment allocation: Two fictional arms, Treatment A and Control B, with 15 participants assigned to each arm.
- Allocation: A fixed, reproducible synthetic allocation generated with a documented random seed.
- Demographics: Age and sex recorded using the study's predefined categories.
- Consent: Consent date and status are recorded. Study-specific procedures must not precede valid consent under the fictional protocol.
- Data domains: Participants, visits, laboratory results, and adverse events.

The study design and all records are fictional. The treatment allocation is for demonstrating data-management checks, not for evaluating a real intervention.

## 12. Validation Rule Framework

Every validation rule will include:

- Rule ID
- Rule name
- Applicable data domain
- Exact validation condition
- Severity: Error or Review
- Expected action
- Test case and expected result

Error: A defined structural or logical requirement is violated.

Review: A value requires investigation but cannot be classified as incorrect solely by an automated rule.

## 13. Cross-Domain Validation

The validation engine will check relationships across the four data domains, including:

1. Laboratory records referring to nonexistent participants.
2. Laboratory records associated with missing or incomplete visits.
3. Laboratory collection dates inconsistent with their visit dates.
4. Adverse-event onset dates preceding consent.
5. Duplicate participant, visit, laboratory, or adverse-event identifiers.
6. Visit dates outside the predefined study windows.
7. Treatment allocation inconsistent with the participant allocation register.

A failed cross-domain check generates a documented discrepancy; it does not automatically authorize a data correction.

## 14. Seeded-Defect Testing

A separate defect register will define the deliberately introduced test defects before validation is run.

Each entry will specify:

- Defect ID
- Target record and field
- Defect category
- Injected condition
- Expected validation rule
- Expected severity
- Expected detection outcome

The initial test suite will contain 12 seeded defects. The final register will be established before generating the test dataset and kept separate from the validation inputs.

Detection performance will be measured by comparing detected issues against the seeded-defect register. Unseeded discrepancies will also be reported separately.

## 15. Query Lifecycle

Permitted statuses:

- Open
- Answered
- Resolved
- Closed
- Cancelled

Simulated roles:

- Data Manager: Reviews discrepancies and oversees query resolution.
- Site Investigator/Coordinator: Provides clarification or supporting information.
- Data Reviewer: Verifies the documented resolution.
- System Validator: Runs automated checks and generates discrepancy records.

These are simulated responsibilities, not claims of real clinical trial system access.

## 16. Reproducibility and Execution

The project will use a fixed random seed for synthetic data generation. Package versions will be recorded in requirements.txt.

The documented execution sequence will be:

1. Review the study specification and data dictionary.
2. Generate synthetic raw data.
3. Run automated validation.
4. Produce the discrepancy report.
5. Populate and review the query log.
6. Document simulated resolutions.
7. Re-run validation on the revised dataset.
8. Generate the final quality summary.

Raw input data will remain unchanged. Revised records and change history will be stored separately.

## 17. Quality Metrics

The final report will include:

- Number of records reviewed.
- Number of seeded defects planted and detected.
- Detection rate for seeded defects.
- Discrepancies by domain and severity.
- Open, answered, resolved, closed, and cancelled query counts.
- Simulated query turnaround time.
- Remaining unresolved discrepancies.
- Validation test pass/fail results.

Query turnaround will be measured in simulated elapsed days, not represented as actual clinical trial performance.

## 18. Role of Excel and Python

Excel will be used for structured data review, dropdown-based entry controls, filtering, query tracking, and human-readable reports.

Python will be used for reproducible data generation, automated validation, cross-domain checks, discrepancy exports, and summary metrics.

The two tools serve complementary purposes. Excel controls do not replace database access controls, electronic signatures, or a validated electronic data capture platform.
